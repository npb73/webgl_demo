# Часть I. WebGL в коде

## 1. WebGL в коде — 2 мин

**На слайде:** «Весь WebGL — это объект `gl`. Сначала настраиваем, потом говорим «рисуй»» + функция `draw`.

> Весь WebGL — это методы одного объекта `gl`. Мы не описываем сцену, как в
> DOM. Мы переключаем глобальное состояние: какая программа, какие вершины,
> какие параметры — и говорим «рисуй».
>
> Пройдите по строкам `draw` сверху вниз. `drawArrays` не принимает ни программу,
> ни буфер — он берёт то, что привязано сейчас. Это главное отличие от
> привычных API, и на нём же половина багов.
>
> Сцен, камер, света нет. Матрицы, освещение, анимация — ваш код.

## 2. Шейдер и JS — 3 мин

**На слайде:** конвейер + пары «объявление в GLSL — вызов в JS».

> Шейдер — это функция, которую GPU вызывает много раз. Вершинный — на каждую
> вершину, возвращает позицию (`gl_Position`). Дальше GPU сам находит пиксели
> внутри треугольника, и фрагментный шейдер вызывается на каждый, возвращает
> цвет. Красным обведено то, что пишем мы.

Пройдите по таблице, это ключ ко всему остальному коду:

- **`in` / attribute** — своё значение на каждую вершину, читается из буфера.
  `vertexAttribPointer` говорит, как его читать: «по два float на вершину».
- **`uniform`** — одно значение на весь вызов: время, размер, матрица.
  Ставится после `useProgram` — это свойство программы.
- **`out` → `in`** — из вершинного во фрагментный. По пути значение
  интерполируется по треугольнику — так получаются градиенты.
- **`sampler2D`** — текстура: картинка или любые данные. Читается
  `texture(u_page, uv)`. Запомните, на слайде 6 через неё в шейдер попадёт
  сама страница.

## 3. Первый треугольник — 2 мин

**На слайде:** пять шагов, по строке кода.

1. **Контекст** — `getContext("webgl2")` возвращает `null`, если WebGL 2 нет.
   Проверяйте.
2. **Программа** — исходник GLSL передаётся строкой, компилируется прямо в
   браузере. Ошибки компиляции сами не бросаются — об этом на слайде «Слабые места».
3. **Буфер** — typed array копируется в видеопамять один раз.
4. **Атрибут** — как читать буфер. VAO запоминает эту настройку, чтобы потом
   переключать всё одной строкой.
5. **Отрисовка** — `useProgram` + `drawArrays`.

> Целиком это ~60 строк: `first-shader.js` и `lib/webgl/program.js` в
> репозитории. Поэтому обычно и берут библиотеки — но один раз руками
> написать стоит.

## 4. Мой первый шейдер — 4 мин

**На слайде:** `first-shader.frag` + кнопка + пара `.vert` / `.frag` + путь файла до страницы.

Нажмите «Запустить шейдер».

> Это весь фрагментный шейдер. `gl_FragCoord` — координата текущего пикселя,
> делим на размер — получаем 0..1. `u_time` JS кладёт каждый кадр через
> `uniform1f`. Цвет — косинус от координаты и времени, со сдвигом фазы для
> R, G и B — поэтому градиент течёт.

Покажите на стикер под кодом — две первые строки:

> `#version 300 es` — версия языка: GLSL ES 3.00, тот, что в WebGL 2. Она
> обязана быть самой первой строкой. Без неё компилятор решит, что это
> старый GLSL 1.00 из WebGL 1, и не узнает ни `in`/`out`, ни `gl_VertexID`.
> Частая ошибка — шаблонная строка в JS, которая начинается с переноса:
> тогда `#version` уже вторая строка.
>
> `precision highp float` — у фрагментного шейдера нет точности по
> умолчанию, её нужно задать явно.

Дальше — две карточки под кнопкой: почему шейдер — это два файла.

> Шейдер — программа для видеокарты на GLSL, языке, похожем на C. В WebGL
> она всегда из двух частей, потому что у GPU две программируемые стадии
> конвейера — та самая схема со слайда 2.
>
> **Вершинный шейдер, `.vert`**, вызывается на каждую вершину и отвечает на
> вопрос «где?»: пишет положение в `gl_Position`. Это форма — треугольник,
> сетка листа на слайде с переходами, миллион точек на графике.
>
> Дальше GPU сам, без нашего кода, растеризует треугольник: находит пиксели
> внутри него. И для каждого вызывает **фрагментный шейдер, `.frag`** — он
> отвечает «какого цвета?» и пишет `outColor`. Пиксель не знает про соседей,
> поэтому их можно считать параллельно тысячами.
>
> Связь между ними — `out` в вершинном и `in` во фрагментном: значение из
> трёх вершин GPU плавно смешивает по треугольнику. Так из трёх цветов в
> углах получается градиент.

Почему нельзя одним файлом:

- `gl.linkProgram` собирает программу только из пары — одного типа
  `gl.VERTEX_SHADER` и одного `gl.FRAGMENT_SHADER`. Шейдеров «по умолчанию»
  в WebGL нет: без любой половины ничего не нарисуется.
- Расширения `.vert` и `.frag` — только соглашение. Для браузера это две
  строки, а тип задаёт `gl.createShader(...)`.
- Одну половину можно переиспользовать: у всех эффектов окон и у первого
  шейдера общий `fullscreen.vert`, меняется только `.frag`.

> Фрагментный шейдер красит только пиксели внутри треугольника. Значит,
> чтобы закрасить весь canvas, нужен треугольник, который его накрывает, —
> это и есть вся работа вершинного шейдера в первом примере. Он на слайде:
> `fullscreen.vert` не читает вершины из буфера, а вычисляет три угла по
> номеру вершины — 0, 1, 2. Треугольник получается больше экрана, лишнее
> GPU обрезает. Всё, что видно на картинке, рисует `.frag`.

Дальше — схема внизу слайда: как этот файл попадает на страницу.

1. **`first-shader.frag`** — обычный текстовый файл в `shaders/`. Браузер
   GLSL как файл не подключает: ни `<script>`, ни `import` для него нет.
   В WebGL шейдер — это просто строка.
2. **`npm run shaders`** — перед `dev` и `build` скрипт
   `build-shader-wasm.mjs` берёт `.frag` и пару к нему — `fullscreen.vert`,
   если своего `.vert` нет, — и кладёт обе строки в
   `public/shaders/first-shader.wasm`. Это способ доставки, не компиляция:
   в модуле лежит тот же текст GLSL.
3. **`loadShaderSources()`** — по клику `fetch` скачивает `.wasm`,
   `WebAssembly.instantiate` поднимает модуль, и JS читает из его памяти две
   строки: вершинный и фрагментный шейдер.
4. **`createProgram()`** — `shaderSource` + `compileShader` +
   `linkProgram`. Компилирует драйвер видеокарты, прямо в браузере, под
   конкретный GPU. Ошибка здесь не бросается сама — `program.js` читает
   `getShaderInfoLog` и бросает её как `Error`, и React показывает её в окне.
5. **`requestAnimationFrame`** — каждый кадр JS ставит `u_resolution` и
   `u_time` и вызывает `drawArrays(gl.TRIANGLES, 0, 3)`: три вершины — один
   треугольник на весь canvas, и GPU вызывает `main()` из `.frag` для каждого
   его пикселя. Размер буфера canvas следит за CSS-размером через
   `ResizeObserver`, с учётом `devicePixelRatio`.

> В React это компонент `ShaderCanvas`: `useEffect` запускает шейдер, а
> функция очистки останавливает цикл и удаляет программу. С флагом
> HTML-in-Canvas тот же шейдер рисует сцена — в текстуру окна, а не в
> отдельный canvas.

Если спросят, зачем `.wasm`, а не `.glsl` рядом: можно и строкой через
`fetch` или импорт сборщика. Здесь `.wasm` — эксперимент с доставкой;
выполняет шейдер всё равно GPU как обычный GLSL.

## 5. Миллион точек — 3 мин

**На слайде:** `scatter.vert` + кнопка. Откройте график, покрутите колесом,
потаскайте, двойной клик — сброс.

> Миллион точек, синтетические данные генерируются в браузере. Позиции —
> `Float32Array`, загружаются в буфер один раз.
>
> Что происходит на кадр при зуме: два `uniform2f` — центр и масштаб — и
> один `drawArrays(gl.POINTS, 0, N)`. Всё. Посмотрите на шейдер: позицию
> каждой точки пересчитывает он, `(a_position − u_center) * u_scale`.
> JS данные не трогает.
>
> Вывод для своих задач: если на каждом кадре вы обходите массив в JS — это
> кандидат на перенос в шейдер.

# Часть II. Страница как текстура

## 6. Шейдер поверх страницы — 6 мин

**На слайде:** «WebGL не видит DOM» + цепочка API + кнопки окон + пять шагов с кодом.

> Шейдеру доступны только буферы и текстуры, DOM он не видит. Но есть
> экспериментальный API HTML-in-Canvas: дети `<canvas layoutsubtree>`
> верстаются как обычный HTML, а их отрисовку можно положить в текстуру
> через `texElementSubImage2D`.
>
> Вот почему вся страница — один canvas. Текст, шрифты, ховеры, выделение —
> настоящие, но картинка идёт через WebGL. А окно получает участок страницы
> под собой как `sampler2D` и решает, откуда брать каждый пиксель.

Откройте окна по очереди, водите ими по тексту и друг над другом:

- **Линза** — пиксель на расстоянии `r` от центра берёт цвет из
  `r · (1 − k + k·r²)`: в центре увеличение, у края смещение пропадает.
  У R, G и B чуть разный `k` — отсюда радужная кайма.
- **Стекло** — каждый осколок по-своему сдвигает и поворачивает картинку.
- **Рябь** — смещение по наклону волновой поверхности.
- **Огонь** — фрактальный шум, движущийся вверх, и цветовая шкала.

> Окна видят и друг друга: подложка — всё, что нарисовано под окном, включая
> другие окна.

Теперь — как это сделано. Пролистайте пять шагов, по экрану на шаг; наведите
на строку кода, если нужна подсказка.

1. **Страница — внутри canvas.** Вся страница — `div drawable` внутри
   `<canvas layoutsubtree>`. Браузер верстает её как обычно, но на экран не
   выводит: это наша работа.
2. **Страница → текстура.** На событие `paint` вызываем
   `texElementSubImage2D` — это `texSubImage2D`, у которого источник —
   DOM-элемент. На странице один слайд размером с экран — его и снимаем,
   размер — в пикселях устройства, чтобы текст был чётким.
3. **Подложка.** Окну нужна не вся страница, а то, что под ним. Сцена
   перерисовывает этот участок — страницу и окна ниже — в отдельную
   текстуру через framebuffer. Отсюда «линза видит другие окна».
4. **Подложка → `sampler2D`.** Текстура кладётся в слот 0
   (`activeTexture` + `bindTexture`), `uniform1i(uPage, 0)` говорит
   шейдеру, где её читать. Дальше тот же полноэкранный треугольник, что в
   первом шейдере.
5. **Искажение.** Ключевая мысль: шейдер ничего не рисует поверх — он для
   каждого пикселя выбирает, *откуда* в подложке взять цвет. Функция
   `fisheye` — вся линза; у R, G и B чуть разный `k`, отсюда радужная кайма.

> Стекло, рябь и огонь — те же пять шагов, отличается только формула в
> шаге 5. И Milkdrop на следующем слайде — тоже: он просто берёт ещё и
> прошлый кадр окна.

Флаг: в Chrome `chrome://flags/#canvas-draw-element`; без него страница — обычный DOM.

## 7. Шейдеры из Winamp — 3 мин

**На слайде:** `main` шейдера + шесть кнопок. Откройте 2–3 окна.

> Кто помнит Milkdrop в Winamp? Это его пресеты, через библиотеку butterchurn.
> Пресет — это не картинка, а поле движения на сетке 48×36: для каждого узла
> — откуда брать пиксель с прошлого кадра.
>
> Шейдер — цикл обратной связи. Берём прошлый кадр окна (`u_previous`) по
> полю движения, подкрашиваем его и подмешиваем 7% свежей страницы
> (`u_page`). Кадр за кадром страница течёт и оставляет цветной шлейф,
> но текст под окном всё равно видно.
>
> Цвет у каждого пресета свой — это функция `paint()`: тепловая карта, радуга
> по углу, ромбы арлекина, дуотон, кольца.

Технически: «прошлый кадр» — это рендер в текстуру через framebuffer и обмен
двух текстур местами каждый кадр (ping-pong).

## 8. Переходы с геометрией — 2 мин

**На слайде:** «Страница — текстура. Переход — любая геометрия» + три кнопки + функция `curl`.

> Раз страница — текстура, переход между слайдами не обязан быть сдвигом
> или затуханием, как в View Transitions. В момент листания у нас две
> текстуры: копия слайда до листания и сама страница после. Слайд
> сменяется мгновенно — новый уже на месте и кликается, — а переход только
> показывает путь.

Весь доклад слайды уже перелистывались — это он и есть. Нажмите
«Перелистнуть»: кнопка листает на следующий слайд. Вернитесь стрелкой ← —
лист ляжет обратно.

> Страница здесь — сетка 96×60 клеток, а не прямоугольник. Вершинный
> шейдер — функция `curl` на слайде: точки за линией сгиба наматываются на
> цилиндр и ложатся обратно перевёрнутыми. Глубина нужна, потому что загиб
> закрывает сам себя. Обратная сторона — та же текстура, осветлённая и
> зеркальная: бумага тонкая.

Дальше «Повернуть куб» и «Рассыпать»:

- **Куб** — две грани по одной клетке: поворот вокруг горизонтальной оси,
  перспектива и свет сверху, чтобы читался объём.
- **Частицы** — `gl.POINTS`, по точке на квадрат 5×5 пикселей, ~50 тысяч
  точек. Каждая показывает свой кусочек страницы и улетает по волне.

После демо нажмите «Перелистнуть», чтобы вернуть его на стрелки, — или
оставьте куб или частицы до конца доклада.

## 9. Коллекционные карточки — 3 мин

**На слайде:** «Карточка товара — HTML. Блеск — шейдер» + три карточки +
голограмма из `product-card.frag`.

Наведите на каждую карточку и поводите указателем, нажмите «В корзину».

> Это уже не демо ради демо, а то, что можно взять в магазин. Карточка —
> обычная разметка: название, цена, рабочая кнопка. Но каждая карточка — свой
> drawable-слой, как окна. Сцена снимает её в текстуру и рисует сама:
> наклоняет за указателем с перспективой и накладывает эффект. Эффект видит
> только пиксели карточки — страница вокруг не меняется.

- **Голограмма** — сама карточка тонируется радугой, которая бежит при
  наклоне, от указателя расходятся кольца, а узор из звёздочек вспыхивает,
  когда наклон попадает в их угол. Важная деталь: на белом простое осветление
  не видно, поэтому шейдер не осветляет, а тонирует снимок.
- **Золотая фольга** — шейдер видит, какие пиксели светлые: буквы и рамка на
  тёмной карточке становятся металлом с бликом, а из-за картинки расходятся
  золотые лучи, которые бегут по кругу при наклоне.
- **Призма** — карточка бьётся на треугольные грани, каждая сдвигает картинку,
  а красный и синий расходятся.

> Обратите внимание на кнопку: карточка наклонена, а кнопка нажимается. Для
> хит-теста сцена сообщает браузеру положение карточки без наклона — при 14°
> кнопка всё равно под указателем.

Технически: место в вёрстке держит пустой блок, а сама карточка лежит прямо в
canvas. Каждый кадр сцена берёт координаты пустого блока — поэтому карточки
прокручиваются вместе со страницей. Перед кадром карточки впекаются в
текстуру страницы, так что переходы и линзы видят их как её часть.

Если спросят, что было сложного: шейдер не слинковался, потому что `u_mode`
объявлен в обоих шейдерах, а `int` по умолчанию в вершинном `highp`, во
фрагментном — `mediump`. Помогла одна строка `precision highp int`.

## 10. Скриншот страницы — 2 мин

**На слайде:** «Скриншот — это просто кадр WebGL» + кнопка + `readPixels`.

Перед кнопкой откройте окно-линзу со слайда 6 и поставьте его на текст.
Нажмите «Сделать скриншот», дождитесь миниатюры справа внизу и нажмите её.

> Вспышка и миниатюра — как в macOS, а снимок — честный: в нём линза, окна и
> голограммы. Мы ничего не «фотографируем»: страница уже нарисована нашим
> WebGL, и кадр лежит в видеопамяти. `readPixels` копирует его в JS, дальше
> обычный 2D-canvas кодирует PNG.
>
> Помните вопрос, можно ли снять обычный DOM? Нельзя: браузер не отдаёт
> скрипту пиксели страницы — там бывают чужие картинки, посещённые ссылки,
> автозаполнение. Без флага эта кнопка неактивна именно поэтому. html2canvas
> не снимает, а перерисовывает страницу по CSS заново — и линзу он бы не
> увидел.

Две детали в коде:

- **Читать — сразу после отрисовки.** Без `preserveDrawingBuffer` буфер
  очищается после показа кадра, поэтому сцена снимает кадр в конце того же
  обработчика `paint`.
- **Строки перевёрнуты.** У WebGL начало координат внизу, у картинки —
  вверху: кадр переворачивается построчно.

Файл называется как в macOS: «Снимок экрана <дата> в <время>.png».

## 11. Как устроен этот сайт — 3 мин

**На слайде:** «Браузер верстает, WebGL рисует» + схема из пяти шагов + обработчик `paint`.

> Обещал в начале объяснить, почему вся страница — один canvas. Вот схема.
>
> React рендерит обычную разметку, но внутрь `<canvas layoutsubtree>`.
> Браузер её верстает и рисует как всегда — только не на экран, а для нас.
> Когда что-то перерисовал, он шлёт canvas событие `paint`. Дальше
> обведённое красным — наш код, `stage-renderer.js`.

Пройдите по обработчику `paint`:

1. **Снимок** — `texElementSubImage2D` кладёт в текстуру открытый слайд.
   Только если браузер его перерисовал — это говорит
   `event.changedElements`. Рамки окон снимаются так же, по одной.
2. **Хит-тест** — `updateElementGeometry` сообщает браузеру, где мы нарисовали
   каждый слой. Поэтому клики, ховер и выделение текста попадают куда надо,
   хотя картинку двигает шейдер. Порядок вызовов — это z-порядок.
3. **Эффекты** — каждое окно рисует свой шейдер в свою текстуру через
   framebuffer. Подложка окна — всё, что под ним: страница и нижние окна,
   поэтому линзы видят друг друга.
4. **Кадр** — страница, рамки и эффекты собираются одним проходом.
   Следующий кадр просим, только пока что-то движется.

> Ещё три решения. Окно двигается матрицей в uniform — React при
> перетаскивании не перерисовывается. Один WebGL-контекст на всё: страница,
> график, Milkdrop и переходы делят текстуры. И без флага страница — обычный
> DOM: на сервере всегда DOM, а сцена включается только после проверки API.

## 12. Сколько это стоит — 3 мин

**На слайде:** «В покое — бесплатно. Дорог только снимок страницы» + таблица
замеров + выводы + живой монитор сцены.

> Я замерил одни и те же действия в двух режимах: обычный DOM и наша сцена.
> Chrome 155, MacBook Pro M3 Pro, ретина. Главный поток — время всех задач
> вкладки, «наш код» — обработчик paint.

Пройдите по таблице сверху вниз:

- **Покой** — сцена не рисует ни одного кадра: около 1 % потока, как у DOM.
- **Прокрутка длинной страницы** — выделенная строка, так сайт был устроен
  до перехода на слайды, и здесь вся цена: 60 снимков в секунду по
  12,5 мс, 79 % главного потока против 4,5 % у DOM. 60 кадров держатся, но
  запас до бюджета кадра — 4 мс. На слабом ноутбуке прокрутка начала бы
  дёргаться.
- **Окно, карточка, куб** — меньше миллисекунды нашего кода на кадр. Снимков
  почти нет: двигаются матрицы, остальное считает видеокарта.
- **Видеопамять** — текстура размером с экран на ретине около 17 МБ. В покое
  33 МБ, во время перехода до 97 МБ.

> Самое неожиданное: на обычном экране, DPR 1, снимок почти такой же — 12 мс.
> Значит, платим не за пиксели, а за то, что браузер заново отрисовывает всю
> страницу — она у нас почти 27 тысяч пикселей в высоту. Вывод для проекта:
> не кладите в canvas всю длинную страницу. Поэтому сайт и стал
> презентацией: на странице один слайд размером с экран, и листание стоит
> один снимок, а не 60 в секунду.

Покажите монитор внизу: в покое он показывает 1 кадр в секунду — это он сам
обновляет текст. Перелистните слайд или поводите окном — цифры вырастут.

Если спросят про видеокарту: время на GPU здесь не измерено — счётчики видят
только главный поток.

# Часть III. В свой проект

## 13. Слабые места — 3 мин

**На слайде:** «WebGL молчит, когда что-то не так» + семь пунктов: что
происходит, что делать и строка кода.

> У каждого пункта одна схема: в чём подвох и как от него защититься. Первые
> пять — про сам WebGL, последние два — про подход «страница — текстура».

- **Глобальное состояние** — в WebGL нет «нарисуй этот объект», есть
  «нарисуй тем, что сейчас привязано». Чужой код перепривязал буфер — вы
  рисуете не то, и ошибки не будет. Лечится привычкой: привязывать всё
  перед отрисовкой, а настройку вершин держать в VAO.
- **Ошибки молчат** — опечатка в GLSL даёт пустой экран, а не исключение.
  Проверяйте `COMPILE_STATUS` и бросайте `getShaderInfoLog` сами, как в
  `program.js`. Остальное — `gl.getError()`, но только при отладке: он
  тормозит.
- **Число вызовов** — видеокарте всё равно, сколько вершин, а драйверу не
  всё равно, сколько draw call'ов. Это ровно урок слайда 5: миллион точек —
  один вызов.
- **Мыло на ретине** — у canvas размер в CSS и размер буфера — разные вещи.
  По умолчанию буфер 300×150. Ставьте его из `ResizeObserver` с учётом
  `devicePixelRatio` и не забывайте `gl.viewport`.
- **Контекст могут отобрать** — сбой драйвера или нехватка памяти, и все
  ресурсы пропали. Честно: на этом сайте это не обработано, поможет
  перезагрузка. В продукте — `webglcontextlost` + `preventDefault()` и
  пересоздание в `webglcontextrestored`.
- **HTML-in-Canvas — эксперимент** — только Chrome и только за флагом. Поэтому
  сайт без флага остаётся обычной страницей: сцена — улучшение, а не
  условие.
- **Каждое изменение — снимок** — страница попадает на экран только через
  текстуру, так что листание и ховер — это пересъёмка. Цифры — на прошлом
  слайде: снимок длинной страницы — 12,5 мс, при прокрутке три четверти
  потока.

## 14. HTML-in-Canvas + шейдеры — 3 мин

**На слайде:** «DOM — источник правды, шейдер — только картинка» + восемь правил.

> Это то, чему научил этот сайт. Главная мысль — в заголовке:
> контент живёт в DOM, шейдер только решает, как его показать.

- **Сначала DOM** — проверяйте `requestPaint` и `texElementSubImage2D`. Нет
  API, сервер или гидратация — обычная страница. Сцена — улучшение, не
  условие.
- **API — за обёрткой** — он экспериментальный и меняется: `layoutsubtree`
  уже переименовали в `content="drawable"`, а Chrome пока игнорирует
  `canvasTransform`. У нас всё это — в `html-in-canvas.js` и проверке
  `detectGeometryMode`.
- **Где нарисовано — там кликается** — каждый слой, который сдвинул шейдер,
  сообщайте через `updateElementGeometry`, по z-порядку. Забыли — клик
  уходит в пустоту, а скринридер показывает рамку не там.
- **Снимок — по изменению** — `changedElements` вместо снимка на каждом
  кадре; длинную страницу показывайте по экрану, как здесь слайды.
- **Двигайте матрицей** — смена CSS `transform` заставляет браузер заново
  снимать элемент. Положение слоя — uniform, геометрию для хит-теста
  обновляем, когда окно остановилось.
- **Кадр по требованию** — `requestPaint()` на листание, ввод и анимацию.
  Статичная страница не грузит GPU. `prefers-reduced-motion` — без анимаций
  и без переходов.
- **Чёткий текст** — буфер и текстуры в пикселях устройства
  (`devicePixelContentBoxSize`), слой в покое — без наклона и по сетке
  пикселей, альфа premultiplied — иначе вокруг букв тёмная кайма.
- **Шейдер — только картинка** — текст остаётся в DOM: Ctrl+F, выделение и
  скринридеры работают. Не запекайте контент в текстуру, которую видит
  только GPU.
